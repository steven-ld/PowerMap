# PowerMap v0.9.0

Release date: 2026-07-31

## Highlights

- New installations keep P2P direct paths first. When a direct path is unavailable, they register
  with PowerMap's built-in official relay; if that relay cannot register or later goes offline,
  iroh's default relays are dynamically added as a resilience fallback.
- Add the **Force relay** setting. It disables P2P/IP transport for both access and expose
  endpoints, so a PowerMap restart is required after changing it.
- The dedicated Relay page distinguishes the official default, custom primary relays, and
  forced-relay state. Each custom relay has an independent token, and the page can concurrently
  measure each configured relay's DNS, TLS, and HTTP latency. Explicit relay sharing includes the
  custom entries and forced-relay choice.

## Compatibility

Existing `[relay]` configurations remain valid. A missing `force_relay` field defaults to `false`.
The former `urls` and `auth_token` fields are read as entries that share the legacy token, and the
next save emits the new `[[relay.relays]]` format. Custom relay entries still form the primary
relay set and do not automatically fall back to iroh; each token is sent only to its corresponding
custom URL. Relay latency probes do not send or validate those tokens.

The access management listener now accepts loopback addresses only. Existing remote-management
deployments should keep PowerMap bound to `127.0.0.1` or `::1` and use SSH forwarding or a local
mTLS reverse proxy.
The official relay client identifier is embedded in the application and is deliberately not an
authorization boundary for private services.
